Vera Rubin · Native LUT-B · Accuracy first

Can Vera Rubin run accurate 3-bit LLM inference?

We study one question: can Rubin's native LUT-B instruction run 3-bit model weights and 3-bit KV cache without destroying model quality?

Answer: yes—but only with the right quantizer. Calibrated non-uniform codebooks and scales keep the quality loss bounded. Naive 3-bit quantization collapses. The algorithm, not the bit width alone, decides whether INT3 works.

Rubin LUT-B and our algorithm

The “B” in LUT-B means matrix operand B, not bit width. Rubin keeps A as an E4M3 matrix and reconstructs compressed B inside the tensor-core MMA.

What Rubin provides A native decompress::lut::b MMA. Each 3-bit index selects one of eight E4M3 values held in tensor memory, so there is no separate dequantization kernel and no dense B tensor.
What we provide The offline quantizer that chooses the eight values, the index of every element, and the scale layout; plus the runtime mapping that makes model weights or cached K/V the compressed B operand.
1 · ConditionOptionally rotate or rescale the tensor to reduce outliers.
2 · FitLearn eight E4M3 reconstruction values for each tile.
3 · CorrectOptionally use RMS², Fisher, or GPTQ to protect important errors.
4 · PackStore 3-bit indices, the 8-value LUT, and UE8M0 scales.
5 · ExecuteRubin looks up B inside the MMA; A remains E4M3.
One K64×N8 tile contains 512 three-bit indices (192 B), one eight-entry E4M3 LUT (8 B), and scale metadata: about 3.2 bits per weight. No dense BF16 weight is materialized in the native path.

How the kernel computes the product

The kernel computes the normal product Y = A·B, but B is reconstructed from the payload only inside each MMA.

B̂[k,n] = global × scaleB[t,n] × LUT[t][index[k,n]]
Y[m,n] = Σₜ Dₜ[m,n] × scaleA[m,t] × scaleB[t,n] × global
1 · Tile the GEMM. One 128-thread CTA owns an M128×N8 output tile and walks K in 64-element segments. Activations are quantized per row/K block to E4M3 plus a UE8M0 scale.
2 · Stage the payload. The 3-bit indices are rearranged into the 256-byte shared-memory image expected by the instruction. The corresponding eight-value LUT and A fragment are staged in tensor memory.
3 · Issue native LUT-B. The kernel executes tcgen05.mma…decompress::lut::b. Hardware looks up B and accumulates an FP32 partial D; an mbarrier prevents reading D before the MMA completes.
4 · Apply scales. The epilogue multiplies each partial by activation scale, weight scale, and the folded global scale. A two-K32 recipe uses two masked K64 passes because direct K32 LUT-B is not legal on this instruction.

Integration is direct: Qwen/Gemma replace text nn.Linear calls; MiniMax replaces routed-expert W13/W2 GEMMs; KV attention maps compressed Kᵀ and V to B in the QK and PV contractions.

What makes this kernel difficult

B-only decompression. The compressed matrix must be operand B. This constrains the attention schedule: Q×Kᵀ and P×V are legal, while schedules that place long K/V in A cannot use LUT-B directly.
Scale placement. Activation and weight scales vary by tile. Our correctness kernel reads each FP32 partial back before applying scales, so partials cannot remain in tensor memory across the whole K loop.
Small-M utilization. The native M tile has 128 rows. Batch-1 decode or a sparsely routed expert may provide only a few live rows, so production performance requires batching, expert gathering, or a persistent schedule.
Two-K32 and synchronization. Fine K32 scales require two masked K64 passes. TMEM stores, MMA, mbarrier completion, and FP32 reads must also be ordered correctly; the current MiniMax accuracy path uses launch blocking for determinism.

Experiment 1 — 3-bit weights

We compare 18 quantized configurations plus BF16 and A8 baselines, across Qwen3-4B, Gemma4-12B, and MiniMax-M3 at 8K, 64K, and 128K. The question is whether algorithm choice can make native W3A8 usable.

What the compared algorithms do

Lloyd–Max / uniform / NF3. Uniform spaces eight levels evenly; NF3 uses a fixed normal-inspired codebook; Lloyd–Max learns eight centroids from each tile. This isolates whether fitting the codebook matters.
RMS² / SqueezeLLM. RMS² weights reconstruction error by activation second moments. SqueezeLLM instead uses diagonal Fisher information. Both change the codebook fit; neither is GPTQ compensation.
GPTQ / inter-GPTQ. GPTQ uses a block Hessian to push each rounding error into columns not yet quantized. Inter-GPTQ alternates this compensation sweep with refitting the eight-value codebook.
H64 / AWQ / scale variants. H64 spreads outliers with a signed Hadamard transform and applies the matching transform to A. AWQ rescales activation channels and folds the inverse scale into weights; K64/two-K32/global variants change scale granularity.

Every reported quantized GEMM above runs through the native Rubin LUT-B MMA.

Result: 3-bit weights are viable, but a naive codebook can be orders of magnitude worse.

Experiment 2 — 3-bit KV cache

Figure 2 compares five Qwen KV configurations (BF16 plus four compressed recipes) and three Kimi latent-cache configurations. It asks whether a fitted codebook and controlled scales can make native K3V3 accurate while reducing cache traffic.

What the KV algorithms do

Window and sealing. Sink and recent tokens remain BF16. Older K/V are sealed once in 64-token chunks as 3-bit indices, layer-specific LUT values, and scales; decode never writes them again.
Lloyd–Max codebooks. Each layer learns eight non-uniform values from calibration data, placing resolution where K/V values occur. Uniform levels waste codes on sparse tails and collapse PPL.
OSCAR. A calibrated rotation and clipping rule spreads outliers before fitting the codebook. It can improve some models, but adds transforms unless they are absorbed into adjacent projections.
Native attention path. E4M3 Q multiplies compressed Kᵀ; max, exp, sum, and normalization stay FP32; E4M3 P then multiplies compressed V. Both cache reads use B-side LUT decompression.

Result: from PPL, 3-bit KV is practical when the codebook and scale are controlled. Uniform INT3 is not a usable baseline.

Conclusion 1 · W3A8 Most “fancy” quality methods are offline and preserve the one-pass K64 kernel. H64 pays an A transform; two-K32 pays a second MMA pass.
Conclusion 2 · K3V3 A fitted codebook and controlled scales can cut a 1M KV cache from 154.6 GB to 30.2 GB. Actual speed then depends on LUT-B rate and small-M scheduling, not on another dequantization pass.

Why these are real Rubin results

Physical payloads Weights and cached K/V are stored as 3-bit indices, an 8-value E4M3 LUT, and scales—not dense BF16 tensors.
Native instruction The kernel issues tcgen05.mma…decompress::lut::b; decompression happens inside the MMA.
No simulated fallback Published MiniMax runs report sim_fallback_gemms = 0. Simulation and hardware agree on rankings and collapse.

Scope

This is an accuracy study, not an optimized throughput claim. The current kernel is deliberately correctness-first. Faster scheduling, batching, and pipelining are engineering work, not evidence needed for the quality result above.
